# 学校公共校历：完成 C＋左侧筛选栏的静态设计与管理流程

## Problem Statement

学生需要集中查阅学校的节假日、学部考试、比赛、活动及各类截止日，并快速确认时间、地点和适用范围。公开校历需要服务小学部、初中部和高中部，避免把面向特定学部的公共事件与个人日程混为一谈。

目前已有三套视觉方向及部分浏览交互的静态示例。用户已选择 C「轻盈分区」，要求采用左侧学部筛选和 A 方案的事件类型复选框，并明确移除侧栏的小日历。还需要沿用这一最终方向，补齐管理员端及尚未覆盖的详情、媒体、手机与异常状态，形成可交付的完整设计方案。

## Solution

交付一套浏览器可打开的静态 HTML 设计稿及对应产品说明。学生端无需登录，以电脑月历为主，手机使用日程列表；管理员端展示登录、事件管理、草稿、预览、发布和变更流程。使用虚构数据演示这些交互，不接入真实账号、数据库、学校数据或报名服务。

以已选 C 方案为唯一后续设计基准：冷灰背景、湖蓝强调色、白色月历与详情表面、轻圆角；Logo 占位固定左上角。电脑左栏直接从“适用学部”开始，下方为“事件类型”，不再出现小月历或重复的顶部筛选。宽屏右侧展示详情，较窄电脑窗口按需展开详情，手机使用全屏详情。

完成标准：所有下述故事都有可检查的页面、状态或演示路径；既有学生端交互保持可用；新增后台与媒体状态使用同一视觉语言；设计边界与模拟性质在评审说明中清楚标注。

## User Stories

1. As a student, I want 无需登录即可查看公共校历, so that 我能直接获取学校日程。
2. As a student, I want 在电脑上默认看到月历, so that 我能了解整个月的事件分布。
3. As a student, I want 月历以周一开始并显示周末, so that 我能按完整自然周理解安排。
4. As a student, I want 切换上个月、下个月并回到今天, so that 我能查阅过去和未来的事件。
5. As a student, I want 切换月历和日程列表, so that 我能按适合自己的方式阅读信息。
6. As a student, I want 默认看到所有学部与类型的事件, so that 我不会因预设筛选漏掉信息。
7. As a student, I want 从左栏选择小学部、初中部或高中部, so that 我能聚焦自己的学部。
8. As a student, I want 选择学部时仍显示全校事件, so that 我不会漏掉全校适用的安排。
9. As a student, I want 跨多个学部的事件能出现在相应筛选结果中, so that 我能找到所有适用于自己的事件。
10. As a student, I want 使用复选框筛选考试、假期、比赛、活动及截止日, so that 我能按关注的事件类型浏览。
11. As a student, I want 学部、类型和标题搜索同时生效, so that 我能缩小查找范围。
12. As a student, I want 按事件标题搜索, so that 我能直接找到已知事件。
13. As a student, I want 在无匹配结果时看到提示和重置入口, so that 我知道如何恢复浏览。
14. As a student, I want 切换月份、视图与界面语言时保留筛选, so that 我不用重复设置条件。
15. As a student, I want 事件类型同时使用文字和颜色, so that 我不必只凭颜色辨认内容。
16. As a student, I want 看到明确的事件时间或全天标识, so that 我能理解是否需要在特定时刻参加。
17. As a student, I want 跨日事件显示为连续横条并在换周时延续, so that 我能看清完整持续范围。
18. As a student, I want 截止日显示“截止”及具体时间, so that 我不会把它误认为普通活动开始时间。
19. As a student, I want 同一天事件较多时通过“还有 N 项”查看完整列表, so that 月历保持整齐且信息不丢失。
20. As a student, I want 当天展开列表遵循当前筛选且包含跨日事件, so that 我看到的内容与月历一致。
21. As a student, I want 点击事件查看完整名称、时间、地点、适用范围及说明, so that 我能判断事件是否与自己有关。
22. As a student, I want 详情按需显示主办方, so that 我知道事件由谁组织。
23. As a student, I want 没有地点等选填信息时省略对应空行, so that 假期和截止日的详情仍然清楚。
24. As a student, I want 在详情中查看海报, so that 我能阅读补充信息。
25. As a student, I want 看到管理员提供的外部报名链接或二维码, so that 我能前往正确的参与渠道。
26. As a student, I want 清楚知道报名由外部渠道承办, so that 我不会误以为校历能提交或管理报名。
27. As a student, I want 关闭详情后回到原来的日期、筛选与浏览位置, so that 我能继续查看其他事件。
28. As a student, I want 已取消事件保留并标注取消, so that 我能发现此前看到的安排已经失效。
29. As a student, I want 改期事件显示在新日期并在详情显示原时间和更新时间, so that 我能识别安排变化。
30. As a student, I want 默认使用简体中文并能切换英文, so that 我能使用熟悉的界面语言。
31. As a student, I want 缺少当前语言译文时显示已有内容, so that 信息不会因缺少翻译变为空白。
32. As a mobile student, I want 默认看到按日期排列的日程列表, so that 我不必横向拖动七列月历。
33. As a mobile student, I want 使用紧凑的学部、类型筛选及搜索, so that 我也能缩小事件范围。
34. As a mobile student, I want 在全屏详情查看事件并关闭返回列表, so that 长内容仍然易读。
35. As a keyboard user, I want 用键盘操作筛选、事件和关闭按钮并看到焦点, so that 我能完成主要浏览流程。
36. As an administrator, I want 看到独立的登录界面与演示后的管理入口, so that 公开浏览与管理操作有清楚区分。
37. As an administrator, I want 在后台查看全部学部的事件, so that 我能统一维护公共校历。
38. As an administrator, I want 在事件列表辨认草稿、已发布和已取消状态, so that 我能知道哪些内容已对学生展示。
39. As an administrator, I want 新增和编辑事件名称、类型、适用范围及时间, so that 校历能准确表达基本安排。
40. As an administrator, I want 将事件设为全校或一个／多个学部适用, so that 同一公共事件无需重复录入。
41. As an administrator, I want 输入定时、全天、跨日或截止时间, so that 不同事项都有合适的时间表达。
42. As an administrator, I want 按需填写地点、说明和主办方, so that 我能补全必要参与信息而不必填无关字段。
43. As an administrator, I want 分别填写中文和英文内容, so that 双语信息可以独立维护。
44. As an administrator, I want 在编辑与预览中看到海报、报名链接和二维码的展示状态, so that 我能检查学生会看到的内容。
45. As an administrator, I want 保存草稿而不显示到公开校历, so that 我能在准备完成前暂存内容。
46. As an administrator, I want 发布前预览学生端详情, so that 我能检查内容、时间与排版。
47. As an administrator, I want 直接发布事件而无需审核, so that 维护流程保持简洁。
48. As an administrator, I want 在缺少必填项或时间范围不正确时看到字段提示, so that 我能在发布前修正问题。
49. As an administrator, I want 允许不同事件时间重叠, so that 不同学部的并行安排能够正常记录。
50. As an administrator, I want 取消事件时保留公开记录并说明变化, so that 学生不会因事件消失而困惑。
51. As an administrator, I want 改期时保留原时间和更新时间, so that 学生能识别新旧安排。
52. As an administrator, I want 对误录事件执行有明确影响提示的删除操作, so that 我能修正录入错误。
53. As a design reviewer, I want 从同一入口查看电脑、手机和后台设计, so that 我能评审完整流程。
54. As a design reviewer, I want 使用稳定且明确标记的示例数据, so that 我能复现筛选、密集日期、取消与改期状态。
55. As a design reviewer, I want 所有新页面沿用 C＋左侧筛选栏的设计, so that 后续交付不会重新引入被否定的小日历或其他视觉方向。

## Implementation Decisions

- **交付边界**：本 Issue 是完整静态设计稿的规格，不是生产应用开发。后台登录、保存和发布仅演示可见状态；不收集真实凭据，不承诺跨会话保存。评审说明与产品界面分开，避免把实现说明塞入学生操作流程。
- **已有基础**：当前项目是原生 HTML、CSS、JavaScript 方向稿；有共享事件样例、月历、列表、筛选、语言切换与详情逻辑，没有服务端、数据库或真实认证。继续复用既有结构，不为完成设计稿迁移框架。
- **模块划分**：保留设计评审入口、公开校历、筛选、事件详情与示例状态；补齐管理员登录、事件列表、事件编辑、预览及状态变更界面。复用事件信息和展示逻辑，避免学生端与管理预览内容分叉。
- **最终视觉**：沿用 C 的冷灰背景、湖蓝强调色、白色表面和轻圆角。Logo 占位固定左上角。电脑左栏只保留学部筛选、事件类型复选框和相关提示／重置；删除小日历及其月份／学期标题。历史 A、B 可以留在评审区作参考，不作为正式产品的主题选项。
- **响应式**：宽屏为左筛选、主月历、右详情；较窄电脑窗口按需展开右侧详情，优先保证月历可读宽度。手机为紧凑筛选、日程列表和可退出的全屏详情。不得因增加侧栏导致手机横向溢出。
- **领域定义**：“事件”涵盖节假日、考试、比赛、活动、截止日；“活动”为一种事件类型。适用范围不是可见权限。学部固定为小学部、初中部、高中部。
- **筛选逻辑**：学部单选“全部学部”或某学部；某学部的结果包含全校事件与适用于该学部的事件。事件本身可适用多个学部。类型多选，组内取并集；学部、类型与标题搜索之间取交集。重置恢复全部类型、全部学部及空关键词。
- **事件信息**：名称、时间、类型、适用范围必填；地点、说明、主办方、海报、报名链接和二维码选填。全校适用与具体学部选择互斥。名称至少一种语言有值；选填信息缺失时省略对应展示区。
- **双语**：默认简中，界面支持英文；事件内容提供中文与英文输入，缺失时回退到已有内容。无自动翻译。切换语言不清除日期和筛选。
- **日期与时间**：周一起始、公历、学校当地时间。具体学校时区尚未提供，设计稿不猜测地区。支持定时、全天、跨日和精确截止时间；不支持重复规则。演示中的今天固定为 2026-09-19，正式产品未来应使用学校当地当前日期。
- **月历密度**：每格约 3–4 项，跨日条计入可见数量；剩余数量入口展开该日全部匹配事件。跨周条延续展示。时间、状态与完整标题在详情／日程中可获取。
- **详情与媒体**：保留月历上下文。海报放详情，二维码和外部链接作为报名入口，不增加报名表或报名记录。用安全的示例内容演示媒体、缺省内容和长内容状态，不向真实外部服务提交数据。
- **管理权限与流程**：所有管理员可维护所有学部事件，不做审核或学部权限分层。模拟状态包括草稿、已发布、已取消；改期为已发布事件的时间变更提示。演示链路为编辑→草稿／预览→发布→学生端看到内容。
- **发布校验**：校验必填字段和时间顺序；结束时间不能早于开始时间。事件可时间重叠。错误在对应字段附近展示并保留已输入内容。
- **变更与误录**：取消后保留标识与记录；改期迁移到新日期并展示原时间与更新时间。删除用于误录，需明确影响及确认。过去事件仍可按月份查阅。
- **接口与数据**：本轮不新增网络 API、认证协议或数据库迁移。模拟事件状态足以驱动所需页面；生产接口、存储与认证选型不在本规格中提前锁定。

## Testing Decisions

- **用户已确认的边界**：统一从浏览器验收学生端和管理员端的可见交互，后台使用模拟数据；不测试内部函数，不接真实登录或数据库。
- **一个主要测试入口**：沿用现有浏览器可打开的设计入口，通过真实点击、输入、选择与键盘操作检查结果。新增管理页面继续在这一层验收，不额外建立服务层或函数级测试入口。
- **好测试的标准**：检查用户看见和能完成的行为，避免断言内部函数、私有状态、CSS 类名或 DOM 实现形状。视觉检查关注可读性、层级、溢出与焦点，不对动态文字作无意义的逐像素限制。
- **被测模块**：公开月历／列表、学部与类型组合筛选、搜索、详情和报名入口状态、语言切换、手机布局，以及新增的管理列表、编辑、草稿、预览、发布、取消和改期演示。
- **现有验证先例**：已有浏览器人工检查和 JavaScript 语法检查；没有自动化测试框架。既有样例包含 19 项事件，初中部筛选后 13 项，再排除活动类型后 7 项；9 月 23 日展开共 6 项。保留这些数据时可作为回归预期，新增独立演示数据不应悄悄改变基准。
- **核心浏览场景**：默认月历→选择学部→取消某类型→标题搜索→无结果→重置；切换月份／语言／列表时条件一致。跨日与跨周事件连续、同一天溢出数量正确、当天展开遵循筛选。
- **详情场景**：长标题、无地点、只有一种语言、海报、只有链接、只有二维码、两者都有、取消、改期。关闭后保留上下文；示例报名入口不得误导为真实报名成功。
- **管理场景**：演示进入后台→新增→必填校验失败→修正→草稿→预览→发布→公开浏览可见；随后改期与取消，分别验证学生端结果。删除误录需要影响提示与确认。
- **草稿隔离**：模拟公开校历不能展示未发布草稿；管理列表可看到草稿。无需真实鉴权，但设计必须清楚区分这两种可见状态。
- **响应式与可访问性**：检查宽屏、较窄电脑窗口及约 390×844 手机尺寸；侧栏不出现小日历，手机无七列横向挤压。键盘能操作筛选、打开／关闭详情和表单，弹层焦点可恢复，文字状态不只依赖颜色。
- **交付核验**：静态文件可打开，主要演示入口可达；新页面的中英文不遮挡按钮和时间；产品说明清楚区分已实现的模拟交互与未来生产能力。

## Out of Scope

- 真实后端、数据库、持久化、学校数据同步、账号体系、真实登录或学校 SSO、生产部署。
- 平台内报名、报名记录、支付、签到与参与人数管理。
- 个人事件、个人日常课程、个人课表、收藏、订阅、通知及个人日历同步。
- 多级审批、学部级编辑权限、面向特定身份的保密事件。
- 周视图、重复事件规则、自动导入节假日、农历、自动翻译。
- 联系人和通用附件字段；海报及报名二维码属于已确认的选填展示信息。
- 新的视觉方向、正式校徽设计、左栏小日历、学生端拖拽编辑事件。
- 选择或接入 FullCalendar、TOAST UI Calendar、Schedule-X 等生产组件。它们在当前阶段仅作为布局与交互参考。

## Further Notes

- 规格依据用户已确认的访谈、C 方案选择、左栏筛选修订及明确移除小日历的指示；之后的页面设计均以此为准。
- 学校名称、正式 Logo、实际时区和真实事件内容尚未提供；用明确占位和虚构内容继续设计，不把示例日期认作真实校历。
- 当前代码和文档仍在本地工作区、尚未提交到 Git；接手者需具备该工作区的设计基线，不能假设远端已包含原型。本规格不授权自动提交、推送或部署。
- GitHub 调研参考：[FullCalendar](https://github.com/fullcalendar/fullcalendar)、[TOAST UI Calendar](https://github.com/nhn/tui.calendar)、[Schedule-X](https://github.com/schedule-x/schedule-x)。不将日历组件当作现成的学校管理系统。
- 规格投递目标为当前项目的 GitHub Issues，使用 `ready-for-agent` 标签。测试范围已获用户确认，不再重新进行需求访谈。
